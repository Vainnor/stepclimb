# Permission catalog, roles and `Require<P>`

- **Status:** Draft
- **Milestone:** M0
- **Plan:** `docs/plan/technical.md` -> Identity and access (Permissions and roles,
  Provisioning), Tenancy and structure, Data model (access), Testing, How it's built
- **Depends on:** `02-organizations-and-accounts.md` (`OrgScope`, accounts and their paths, API
  conventions), `03-users-and-identities.md` (users, `Source`), `08-sessions-and-csrf.md` (the
  authenticated principal and API key scopes)
- **Review:** maintainer line-by-line

## Summary

This spec defines who may do what. Permissions are a fixed catalog of Rust types in
`stepclimb-core`; roles bundle them (eight built-in roles, plus custom roles an organization
defines); role assignments grant a role to a user at organization, account or course scope.
Handlers check with the typed extractor `Require<perm::X>` before their body runs, and a permission
test suite proves every protected route answers 401, 403, 404 and 2xx correctly and refuses other
organizations' ids.

## Behavior

### The catalog

- **B1.** Every permission is a unit struct in `stepclimb_core::perm` implementing the
  `Permission` trait: `const KEY: &'static str` (the stored and API name, format pending Q1;
  this spec writes `area.action`) and `const GRANTABLE: &'static [ScopeType]` (the scope types
  at which it can take effect). `perm::ALL` lists every entry, generated by the same macro that
  defines the structs, so an entry cannot be defined without being listed. The catalog changes
  only in code; no API or table adds a permission.
- **B2.** The M0 catalog. Entries marked with another spec are listed here so the catalog lives in
  one place; the routes that check them are in that spec.

  | Type | Key | Grantable at | Checked by |
  | --- | --- | --- | --- |
  | `perm::OrgManage` | `organization.manage` | organization | `02` (organization, settings), `10` (entitlements view) |
  | `perm::AccountView` | `account.view` | organization, account | `02` |
  | `perm::AccountManage` | `account.manage` | organization, account | `02` |
  | `perm::UserView` | `user.view` | organization, account | `03` |
  | `perm::UserManage` | `user.manage` | organization | `03` |
  | `perm::RoleView` | `role.view` | organization, account | this spec |
  | `perm::RoleManage` | `role.manage` | organization | this spec (custom roles) |
  | `perm::RoleAssign` | `role.assign` | organization, account | this spec |
  | `perm::ProviderManage` | `provider.manage` | organization | `04` (local method switches), `05`, `06` |
  | `perm::AdmissionManage` | `admission.manage` | organization | `07` |
  | `perm::ServiceAccountManage` | `service_account.manage` | organization | `08` |
  | `perm::BrandingManage` | `branding.manage` | organization | `12` |

  `UserView` is grantable at account scope, where it covers the users who hold a role
  assignment (from M1, also an enrollment) inside the account's subtree; `UserManage` stays
  organization-only (Q2). Later milestones add entries (course content, grading, enrollments, reports) and widen grantable
  scopes to `course` where they apply.
- **B3.** A scope is `Organization` (the caller's organization), `Account(id)` (that account and
  its whole subtree) or `Course(id)` (one course). The scopes nest: a grant at organization scope
  covers every account and course in it; a grant at account A covers A, every descendant of A and
  every course in them; a grant at course C covers C only. A permission granted through an
  assignment at a scope type not in its `GRANTABLE` list has no effect (Organization admin
  assigned at account Tower does not get `OrgManage`).

### Roles

- **B4.** A role has a `key`, a `name`, `builtin` and a list of permission keys. Built-in roles
  are instance-wide rows (`org_id` null); custom roles belong to one organization.
- **B5.** The eight built-in roles, their keys and their M0 permissions:

  | Role | Key | M0 permissions | Plan: "Can" |
  | --- | --- | --- | --- |
  | Organization admin | `org_admin` | every entry in `perm::ALL` | Everything, including providers, branding and integrations |
  | Account admin | `account_admin` | `account.view`, `account.manage`, `user.view`, `role.view`, `role.assign` (Q2, Q3) | Courses, users, roles and reports within an account subtree |
  | Course designer | `course_designer` | none until M1 | Edit content, banks and quizzes |
  | Instructor | `instructor` | Course designer's, plus none of its own until M1 | Designer permissions plus grading, overrides, accommodations and enrollments |
  | Grader | `grader` | none until M2 | Grade submissions and give feedback |
  | Student | `student` | none until M1 | Take enrolled courses |
  | Manager | `manager` | none; its scope (a user's direct and indirect reports) arrives in M4 | See and remind their own reports, receive escalations |
  | Observer | `observer` | none; its scope (named students) arrives with progress in M1 | Read-only view of named students' progress |

  The lists are defined in code (`stepclimb_core::roles::BUILTIN`), with Organization admin
  defined as `perm::ALL` and Instructor as Course designer's list plus its own, so a permission
  added later reaches them without editing two lists.
- **B6.** The server reads a built-in role's permissions from code, never from its database row.
  At startup (before serving, under `OrgScope::instance` rules in `02` B9) the server upserts each
  built-in row by key, writing `name` and `permissions` so SQL readers see the current lists.
  Taking the lists from code means two binaries of different versions during a rolling deploy each
  apply their own lists, and neither rewrites the other's behavior. A built-in row the running
  binary does not define (a newer release's role) grants nothing on that binary and is left as
  it is. When a built-in row the sync is about to insert has the key of a custom role in any
  organization, the sync writes nothing and the server refuses to start, naming the organization
  and the key (coordinator decision, 13 Nov 2026).
- **B7.** Built-in roles cannot be changed or deleted through the API (409
  `role.builtin_immutable`). An organization that wants a variant creates a custom role.
- **B8.** A custom role is created with `key`, `name` and `permissions` by a holder of
  `perm::RoleManage` (organization scope). Its key is unique in the organization and is not a
  built-in key (409 `role.key_taken`); the key format is pending Q7. Its name is trimmed, not
  empty and at most 200 characters, the rule `02-organizations-and-accounts.md` Q6 sets for
  organization and account names (coordinator decision, 13 Nov 2026). Every permission must be in
  `perm::ALL` (422, `errors[].code = "role.unknown_permission"`, field `/permissions/<i>`) and
  appear at most once (422, `errors[].code = "role.duplicate_permission"`, field
  `/permissions/<i>` of the repeat), which bounds a list at the catalog's length (coordinator
  decision, 13 Nov 2026). The
  creator must hold every permission they put in the role at organization scope (403
  `permission.escalation`), so `RoleManage` alone does not let anyone mint a stronger role.
- **B9.** Changing a custom role's `name` or `permissions` follows B8's checks and takes effect
  for every holder on their next request. On a change of `permissions`, the escalation check
  covers every permission the role gains and every permission it loses; a permission the new list
  keeps is not checked, and a change of `name` alone checks none. The route locks the role's row
  for the check and the write, so the list it checks is the list it replaces (coordinator
  decision, 13 Nov 2026). A consequence: a `role.manage` holder who holds a permission K at
  organization scope can add K to a custom role that is already assigned, which gives K to every
  current holder at their assignment's scope (accounts included), without holding
  `role.assign`. A stored permission key that a later release removed
  from the catalog is ignored when evaluating and logged once per startup at `warn`.
- **B10.** A custom role with any assignment cannot be deleted (409 `role.in_use`); the caller
  removes the assignments first.

### Role assignments

- **B11.** An assignment grants one role to one user at one scope and records its `source`
  (`03-users-and-identities.md` B4) with an optional `external_id`. M0 creates only `local`
  assignments; group-mapped, pushed and delegated assignments come with M4's permission modes.
- **B12.** A holder of `perm::RoleAssign` at scope S may create an assignment at S or any scope
  inside S. The request names `user_id`, `role_id` and `scope`. Checks, in order:
  1. the user exists in the caller's organization (else 404 `user.not_found`, whatever the
     caller's user permissions);
  2. the role is built-in or one of the organization's custom roles (else 404 `role.not_found`);
  3. the scope exists in the organization: `organization` must name the caller's organization id,
     `account` an account of the organization (else 404 `account.not_found`); `course` answers 422
     `role_assignment.scope_unavailable` until the M1 courses spec enables it;
  4. the caller holds `RoleAssign` at that scope, mapped to 404 or 403 as in B17;
  5. the caller holds, at that scope, every permission of the role that is grantable there (403
     `permission.escalation`); an account admin cannot hand out Organization admin at its account;
  6. the same `(user, role, scope)` does not already exist (409 `role_assignment.exists`).
- **B13.** Manager and Observer cannot be assigned in M0 (422 `role_assignment.scope_unavailable`):
  their scopes (reports, named students) do not exist yet, and assigning them at organization or
  account scope would mean something the plan does not say.
- **B14.** Removing an assignment needs what creating it would (B12 steps 4 and 5) at the
  assignment's scope. An assignment whose `source` is not `local` is read-only (409
  `role_assignment.externally_managed`). Removing the last organization-scope Organization admin
  assignment held by an `active` user answers 409 `role_assignment.last_org_admin`; recovery from a
  lost admin is `stepclimb admin create` (`02-organizations-and-accounts.md` B27).
- **B15.** Deleting an account deletes the assignments scoped to it
  (`02-organizations-and-accounts.md` B21). Assignments are not deleted when a user is suspended;
  a suspended user's requests fail authentication before any permission check.

### Evaluating permissions

- **B16.** For each request with a principal, the evaluator loads the user's assignments in the
  principal's organization with one query (assignments joined to roles, and to accounts for their
  paths), and turns them into **grants**: per scope, the set of effective permissions (B3, B6, B9).
  No result is cached across requests, so a removed role stops working on the next request. The
  query also filters the joined role to built-in or the principal's organization, and an
  account-scope assignment whose account is not in the organization fails the load rather than
  granting anything, so a row that got past the table's checks cannot grant across organizations
  (coordinator decision, 13 Nov 2026). For
  an API key, the grants are then intersected with the key's scopes as `08-sessions-and-csrf.md`
  defines them, evaluated with the owner's current assignments on every request. A service account
  with no owner user has the rights `08-sessions-and-csrf.md` defines for it.
- **B17.** `Require<P, T = OrgTarget>` is an axum extractor. `P: Permission`; `T: Target` names
  how the target scope is found. It runs before the handler body, in this order:
  1. no authenticated principal: 401 `auth.unauthenticated` (or `08`'s more specific `auth.*` code);
  2. the entitlement check, when the route also takes `Require<Feature>`
     (`10-entitlements-framework.md`);
  3. resolve the target inside the principal's organization; a target that does not exist there
     answers 404 with the target's code (`account.not_found`);
  4. the target is **visible** when the principal holds at least one effective permission at a
     scope that contains it (the organization itself is always visible to its members). Not
     visible: 404 with the same code as step 3, so another scope's ids cannot be told apart from
     ids that do not exist;
  5. visible but `P` is not effective at a scope containing the target: 403 `permission.denied`;
  6. otherwise the handler runs, with the extractor yielding the resolved target and the grants.
- **B18.** Targets in M0:
  - `OrgTarget`: the principal's organization. Steps 3 and 4 always pass.
  - `AccountTarget`: the path parameter `account_id`, resolved through
    `stepclimb_core::accounts::ancestors_path`.
  - `AccountParentTarget`: the parent of `account_id` (for move and delete,
    `02-organizations-and-accounts.md` B23); the root has no parent, so the check fails with 404
    for any caller without organization-scope `AccountManage`, and the handler's own 409
    `account.root_immutable` is reached only by those who hold it.
  - `AnyScope`: for list routes and routes whose target is in the body. Passes step 5 when `P` is
    effective at any scope; otherwise 403. The handler or repository then filters by
    `grants.scopes_with::<P>()`, or calls `grants.require_at::<P>(scope)` for a body target,
    which applies steps 3 to 5 with the same mapping.
  `CourseTarget` arrives with M1's courses spec and resolves a course to its account path.
- **B19.** A protected handler without a `Require` extractor is a bug. The permission suite (B20)
  catches it: the anonymous case of every non-public route expects 401.

### The permission suite

- **B20.** `crates/stepclimb-server/tests/permissions.rs` holds one table entry per protected
  operation: the OpenAPI `operation_id`, the permission, the target kind and a setup function that
  builds the target in a new organization. From each entry the permission suite generates:
  - **401:** no credential;
  - **403:** a user holding a custom role with every catalog permission except `P`, assigned at
    the target's scope (or the organization for `OrgTarget`), so the target is visible;
  - **404:** a user holding a custom role with every catalog permission, assigned at a sibling
    account of the target, so `P` is held but at the wrong scope (recorded as not applicable for
    `OrgTarget` and for organization-only permissions);
  - **2xx:** a user holding a custom role with exactly `P` at the target's scope, proving `P`
    alone suffices (an entry may add permissions the route documents, such as the destination of
    a move);
  - **cross-organization:** an Organization admin of org A calling the route with the target built
    in org B: 404, and org B's rows unchanged. A route without a target (`OrgTarget`, an
    `AnyScope` list, `AuthOnly`) acts on org A instead and answers 2xx. Org B also holds a user,
    a session, a custom role and an assignment; its rows (every table with `org_id`, plus the
    tables scoped through another, such as `sessions` through `users`) stay unchanged, and none
    of its ids, slug, names or emails appears in the response. A table with neither `org_id` nor
    a listed scoping fails the suite until it is listed.

  Each case builds its own organizations in the test's database, so cases cannot disturb each
  other. Because the production resolver answers 404
  `org.not_found` whenever two organizations exist (`02-organizations-and-accounts.md` B11), the
  suite names the request's organization with the `x-stepclimb-test-org` header, which only a
  build with the server's `test-support` cargo feature reads. Only the server's own tests enable
  that feature (a dev-dependency of the crate on itself); the release build ignores the header,
  which the e2e smoke test checks against the Compose image (coordinator decision, 13 Nov 2026).
- **B21.** A walker test reads `openapi::document()` and fails, naming each one, when an
  operation is neither in the suite table nor in the public list (`healthz`, `readyz`, and the
  unauthenticated routes `04` to `08` declare), so a new route cannot skip the four cases. Routes
  that need authentication but no permission (`GET /api/v1/me`) are entries with target kind
  `AuthOnly`, which generate the 401 and 2xx cases only.

## API

Common errors as in `02-organizations-and-accounts.md` -> API.

| Method and path | Request | Response | Errors | Permission |
| --- | --- | --- | --- | --- |
| `GET /api/v1/admin/permissions` | | 200 `PermissionInfo[]` | | `perm::RoleView` (any scope) |
| `GET /api/v1/admin/roles` | `?cursor&limit` | 200 `Page<Role>` (built-in first, then custom by key) | 400 `pagination.invalid_cursor` | `perm::RoleView` (any scope) |
| `GET /api/v1/admin/roles/{role_id}` | | 200 `Role` | 404 `role.not_found` | `perm::RoleView` (any scope) |
| `POST /api/v1/admin/roles` | `{ key, name, permissions: string[] }` | 201 `Role`, `Location` | 403 `permission.escalation`, 409 `role.key_taken`, 422 `request.invalid` | `perm::RoleManage` (organization) |
| `PATCH /api/v1/admin/roles/{role_id}` | `{ name?, permissions? }` | 200 `Role` | 403 `permission.escalation`, 404 `role.not_found`, 409 `role.builtin_immutable`, 422 `request.invalid` | `perm::RoleManage` (organization) |
| `DELETE /api/v1/admin/roles/{role_id}` | | 204 | 404 `role.not_found`, 409 `role.builtin_immutable`, 409 `role.in_use` | `perm::RoleManage` (organization) |
| `GET /api/v1/admin/role-assignments` | `?user_id&scope_type&scope_id&cursor&limit` | 200 `Page<RoleAssignment>` | 400 `pagination.invalid_cursor`, 404 `account.not_found` (scope filter) | `perm::RoleView` (any scope; filtered to visible scopes) |
| `POST /api/v1/admin/role-assignments` | `{ user_id, role_id, scope: { type, id } }` | 201 `RoleAssignment`, `Location` | 403 `permission.escalation`, 404 `user.not_found`/`role.not_found`/`account.not_found`, 409 `role_assignment.exists`, 422 `role_assignment.scope_unavailable` | `perm::RoleAssign` (the scope in the body, B12) |
| `DELETE /api/v1/admin/role-assignments/{assignment_id}` | | 204 | 403 `permission.escalation`, 404 `role_assignment.not_found`, 409 `role_assignment.externally_managed`, 409 `role_assignment.last_org_admin` | `perm::RoleAssign` (the assignment's scope) |

The roles routes check, in order: `Require` (401, 403 `permission.denied`); the role exists and is
custom (404 `role.not_found`, 409 `role.builtin_immutable`); the escalation rule (403
`permission.escalation`, which skips a key outside the catalog); then the role's own rules (422
`request.invalid`, 409 `role.key_taken`, 409 `role.in_use`). A body member the schema does not
name answers 400 `request.malformed`. A 422 lists the first rule the body breaks, with the field
codes `role.key_invalid` (`/key`), `role.unknown_permission` and `role.duplicate_permission`
(`/permissions/<i>`), `name.empty`
and `name.too_long` (`/name`), and `text.contains_nul` (the member holding NUL). `created_at` and
`updated_at` are RFC 3339 in UTC with six fractional digits (`2025-11-13T02:13:20.000000Z`)
(coordinator decision, 13 Nov 2026).

Schemas: `PermissionInfo { key, grantable: ScopeType[] }`; `Role { id, key, name, builtin,
permissions: string[], created_at, updated_at }` (built-in roles report their code lists, B6);
`RoleAssignment { id, user_id, role_id, scope: { type, id }, source, external_id, created_at }`;
`ScopeType = "organization" | "account" | "course"`. The `role.view` filter on assignments shows
an assignment when its scope is visible to the caller and `RoleView` is effective there.

`GET /api/v1/me` carries the caller's grants (`03-users-and-identities.md` B22).

## Data

Migration `migrations/<timestamp>_roles.sql`:

```sql
CREATE TABLE roles (
    id           uuid        PRIMARY KEY,
    org_id       uuid        REFERENCES organizations (id),     -- null for built-in roles
    key          text        NOT NULL,
    name         text        NOT NULL CHECK (btrim(name) <> ''), -- not in the data model: Q6
    builtin      boolean     NOT NULL,
    permissions  text[]      NOT NULL DEFAULT '{}',
    created_at   timestamptz NOT NULL DEFAULT now(),
    updated_at   timestamptz NOT NULL DEFAULT now(),
    CHECK (builtin = (org_id IS NULL))
);
CREATE UNIQUE INDEX roles_builtin_key ON roles (key) WHERE org_id IS NULL;
CREATE UNIQUE INDEX roles_org_key ON roles (org_id, key) WHERE org_id IS NOT NULL;

CREATE TABLE role_assignments (
    id           uuid        PRIMARY KEY,                        -- not in the data model: Q6
    org_id       uuid        NOT NULL,
    user_id      uuid        NOT NULL,
    role_id      uuid        NOT NULL REFERENCES roles (id),
    scope_type   text        NOT NULL CHECK (scope_type IN ('organization', 'account', 'course')),
    scope_id     uuid        NOT NULL,
    source       text        NOT NULL DEFAULT 'local'
                             CHECK (source IN ('local', 'idp', 'sync', 'scim', 'connector')),
    external_id  text,
    created_at   timestamptz NOT NULL DEFAULT now(),
    updated_at   timestamptz NOT NULL DEFAULT now(),
    FOREIGN KEY (org_id, user_id) REFERENCES users (org_id, id),
    UNIQUE (user_id, role_id, scope_type, scope_id),
    CHECK (scope_type <> 'organization' OR scope_id = org_id)
);
CREATE INDEX role_assignments_by_user ON role_assignments (org_id, user_id);
CREATE INDEX role_assignments_by_scope ON role_assignments (org_id, scope_type, scope_id);
```

`roles` is the one table besides `organizations` and `plans` (`10`) where `org_id` can be null:
built-in roles are instance-wide definitions, not organization data, and the check ties
`builtin` to the null. `role_assignments` carries `org_id` (the data model lists
`role_assignments(user_id, role_id, scope_type, scope_id, source)`; the Tenancy section's "every
row carries an `org_id`" adds it). A constraint trigger `role_assignments_role_in_org` refuses a
row whose role has an `org_id` other than the row's. A `BEFORE UPDATE` trigger
`roles_identity_immutable` refuses changing a role's `org_id`, `key` or `builtin`, so a role
never moves between organizations or kinds after it is assigned (coordinator decision, 13 Nov
2026). `scope_id` has no foreign key because it
points at different tables by `scope_type`; the repository checks it (B12 step 3) and account
deletion removes the rows (B15). The courses spec (M1) adds its own deletion rule.

Repository modules (every function takes `OrgScope`, except the built-in sync, commented):
`stepclimb_core::roles` (`list`, `get`, `create_custom`, `update_custom`, `delete_custom`,
`sync_builtin`), `stepclimb_core::role_assignments` (`list`, `create`, `delete`,
`for_user_with_paths` for the evaluator, `count_active_org_admins`).

## Permissions

This spec adds the catalog in B2 and the built-in roles in B5. Its own routes check
`perm::RoleView`, `perm::RoleManage` and `perm::RoleAssign`. Whether custom roles are an
entitlement feature (a `Require<Feature>` on the role-writing routes) is
`10-entitlements-framework.md` Q1.

## Test cases

`#[sqlx::test]` for database tests; route tests through the permission suite (B20).

- **T1** (B1). Unit: every key in `perm::ALL` is unique, matches the key format (Q1's), and has a
  non-empty `GRANTABLE`; adding a struct without the macro fails to compile against `ALL`'s use.
- **T2** (B3). Unit, on the evaluator with in-memory assignments: an organization grant covers
  every account; a grant at Tower covers Ground (Tower's child) but not Enroute or the root; a
  grant of Organization admin at Tower does not yield `organization.manage`.
- **T3** (B5). Unit: `org_admin` is defined as `perm::ALL` and holds every key in it;
  `instructor` is defined as extending `course_designer` and holds every key of it;
  `account_admin` holds exactly `account.view`, `account.manage`, `user.view`, `role.view` and
  `role.assign`.
- **T4** (B6). After startup on an empty database there are eight built-in rows; editing a
  built-in row's `permissions` by SQL and calling the evaluator still yields the code list;
  restarting rewrites the row.
- **T5** (B7). PATCH and DELETE of a built-in role answer 409 `role.builtin_immutable`.
- **T6** (B8). Creating a custom role with key `org_admin` answers 409 `role.key_taken`; with
  `"nonexistent.perm"` answers 422 `role.unknown_permission` at `/permissions/0`; a user holding
  a custom role with only `role.manage` creating a role with `user.manage` answers 403
  `permission.escalation`.
- **T7** (B9). A user's request succeeds, their custom role loses the permission by PATCH, and
  their next request answers 403 (no restart, no cache).
- **T8** (B10). Deleting a custom role with one assignment answers 409 `role.in_use`; after removing
  the assignment it answers 204.
- **T9** (B12). Each check in order: an org B `user_id` gives 404 `user.not_found`; an org B
  custom role gives 404 `role.not_found`; a `course` scope gives 422
  `role_assignment.scope_unavailable`; an account admin of Tower assigning at Enroute gives 404;
  assigning `org_admin` at Tower gives 403 `permission.escalation`; assigning `account_admin` at
  Ground gives 201; repeating it gives 409 `role_assignment.exists`.
- **T10** (B13). Assigning `manager` or `observer` answers 422
  `role_assignment.scope_unavailable`.
- **T11** (B14). Removing the only active Organization admin's organization assignment answers 409
  `role_assignment.last_org_admin`; with a second active admin it answers 204. Removing an
  assignment with `source = 'sync'` (inserted by SQL) answers 409
  `role_assignment.externally_managed`.
- **T12** (B16). An API key whose owner has `account.manage` at Tower but whose scopes (per `08`)
  do not cover it gets 403 on `PATCH /api/v1/accounts/{tower}`; removing the owner's assignment
  makes a key whose scopes do cover it get 404 on the next request.
- **T13** (B17). The order of mapping: a user with no assignments gets 404 on
  `GET /api/v1/accounts/{tower}`; with `account.view` at Ground only (Tower's child) still 404 on
  Tower; with any permission at the root but not `account.view`, 403.
- **T14** (B18). `AnyScope`: a user without `role.view` anywhere gets 403 on
  `GET /api/v1/admin/roles`; `GET /api/v1/admin/role-assignments` for an account admin of Tower
  lists assignments at Tower and Ground and none at Enroute or the organization.
- **T15** (B19, B20). Mutation, done once and recorded in the PR: removing `Require` from one
  route makes its 401 case fail; changing one handler's `P` to another permission makes its 2xx
  case fail.
- **T16** (B21). Adding a route to the router and the OpenAPI document without a suite entry
  fails the walker test with that `operation_id` in the message.
- **T17** (`03-users-and-identities.md` B22). `GET /api/v1/me` for an account admin of Tower
  returns one grant with scope `account`/Tower and the B5 permissions sorted.
- **T18** (every route in API). The permission suite's four cases and the cross-organization case
  for each roles and role-assignments route; for `POST /api/v1/admin/role-assignments` the target is
  the body scope.
- **T19** (Data). A role assignment row with an org B custom role in org A is refused by
  `role_assignments_role_in_org`; an `organization` scope whose `scope_id` is not the row's
  `org_id` is refused by the check.

## Open questions

The owner accepted every recommendation below on 13 Nov 2026. Where a behavior or an issue
says "pending Q<n>" or "Q<n> answered", build the recommended option; the owner can still
overrule one, which then updates this spec.

- **Q1. The permission key format.** Keys are stored in `roles.permissions` and shown in the API,
  so they are hard to change after M0. Options: A, `area.action` in lowercase snake case
  (`account.manage`), matching the problem codes; B, `area:action` (`account:manage`), the shape
  the plan uses for API key scopes (`reports:read`); C, the Rust type name (`AccountManage`).
  `08-sessions-and-csrf.md` uses catalog keys as API key scopes, so whichever format is chosen is
  also the scope format (the plan's `reports:read` would be `reports.read` under A).
  Recommendation: A, matching the problem codes. This spec writes A and changes with the answer.
  **Decided:** the recommendation (owner, 13 Nov 2026).
- **Q2. What "users within an account subtree" means for Account admin.** `users` has no account
  column. Options: A, user permissions stay organization-only and Account admin has none (it can
  still assign roles to a user whose id it is given); B, a user is "in" an account when they hold
  any role assignment or (from M1) an enrollment inside it, and `UserView`/`UserManage` at account
  scope apply to those users; C, add a home account to users (a column the data model lacks).
  Recommendation: B for `UserView` (an account admin can find the people in their subtree) and A
  for `UserManage` (editing or suspending a person affects the whole organization).
  **Decided:** the recommendation (owner, 13 Nov 2026).
- **Q3. Account admin and custom roles.** The plan gives Account admin "roles". This spec reads
  that as viewing roles and assigning them inside the subtree, with defining custom roles
  (`role.manage`) left to organization scope, since a custom role is an organization-wide
  definition. Options: A, as written; B, let account admins define custom roles too (they would be
  visible organization-wide). Recommendation: A.
  **Decided:** the recommendation (owner, 13 Nov 2026).
- **Q4. The escalation rule (B8, B12, B14).** The plan does not state one. Options: A, as written:
  to grant, define or remove a role you must hold its permissions at that scope; B, `RoleAssign`
  alone suffices, relying on who is given `RoleAssign`. Recommendation: A; without it an account
  admin can make anyone Organization admin of their subtree with more rights than their own.
  **Decided:** the recommendation (owner, 13 Nov 2026).
- **Q5. Audit entries in M0.** `audit_events` is in the data model and the plan audits grants and
  grade changes, but M0's milestone does not list auditing. Options: A, add `audit_events` in M0
  and write one entry per role, assignment, account, user status and organization settings change;
  B, wait for the milestone that names audit (M2 for grades, M6 for grants). Recommendation: A,
  since permission changes are the first thing a reviewer of an incident asks for.
  **Decided:** the recommendation (owner, 13 Nov 2026).
- **Q6. Columns this spec adds beyond the data model.** `roles.name` (the data model has only
  `key`; alternative: the key is the label, and built-in labels come from ICU messages);
  `role_assignments.id` (alternative: address an assignment by its natural key in a `DELETE
  /api/v1/admin/role-assignments?user_id&role_id&scope_type&scope_id`); `created_at` and
  `updated_at` on both, per the data model's own "everywhere". Recommendation: keep all four.
  **Decided:** the recommendation (owner, 13 Nov 2026).
- **Q7. The custom role key format.** Options: A, `^[a-z][a-z0-9_]{0,62}$`; B, any non-empty
  string up to 64 characters. Recommendation: A, matching the built-in keys.
  **Decided:** the recommendation (owner, 13 Nov 2026).
