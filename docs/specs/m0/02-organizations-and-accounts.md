## Summary

This spec gives Stepclimb its tenant and its structure: the `organizations` row every other row
is scoped to, the `OrgScope` type every repository function takes, and the tree of accounts inside
an organization (like Canvas sub-accounts), stored with an `ltree` path. It adds the read and
admin API for the organization and its accounts, and the shared API conventions (problem
details, cursor pagination, UUID v7 keys) that every M0 endpoint uses.

## Behavior

### Shared API conventions

These apply to every endpoint in M0, including the ones other specs define.

- **B1.** Every error response is RFC 9457 `application/problem+json` with the members `type`,
  `title`, `status`, `detail` and a stable `code` string (the naming scheme is pending Q4; this
  spec writes codes as `area.reason`). Validation failures (422) add `errors`, a list of
  `{ "field": "<JSON Pointer>", "code": "<code>" }`. No error response carries a stack trace,
  SQL text, a secret or an id the caller could not otherwise see.
- **B2.** Request bodies that are not JSON answer 415 `request.unsupported_media_type`; JSON that
  does not parse or does not match the schema answers 400 `request.malformed`; a body that parses
  but breaks a rule (an empty name, an unknown setting) answers 422 `request.invalid`. A body
  over the server's size limit (axum's default, 2 MiB) answers 413 `request.too_large`. A path or
  query parameter that does not parse (an id that is not a UUID, `limit=abc`) answers 400
  `request.malformed`. A path under `/api/` that no route matches answers 404
  `request.not_found`, and a matched path with a method it does not take answers 405
  `request.method_not_allowed` with an `Allow` header. Anything the server fails at answers 500
  `internal.error`, whose `detail` is a fixed sentence; the cause goes to the log. axum's own
  rejections are converted to these, so no plain-text error leaves the server.
- **B3.** Every list endpoint uses cursor pagination: query parameters `cursor` (opaque) and
  `limit`; the response is `{ "items": [...], "next_cursor": "<opaque>" | null }`. A cursor is
  the base64url encoding of the last item's sort key; the server never trusts it to imply an
  organization (the scope still comes from the credential, B9). A cursor that does not decode
  answers 400 `pagination.invalid_cursor`. `limit` defaults to 50 and allows 1 to 200 (Q6); a
  value outside that range is refused with 400 `request.malformed`, not clamped. The cursor is
  not signed, so a client can read and edit it: a list's sort key holds only fields every
  caller of that list already sees in the item.
- **B4.** Every key is a UUID v7 generated by the server (PostgreSQL 16 has no `uuidv7()`), so
  keys sort by creation time and keyset pagination by `id` is stable. The client never supplies
  a key on create. The generating library is pending Q7.
- **B5.** Every table has `created_at` and `updated_at` (`timestamptz`, `NOT NULL`, default
  `now()`); repository updates set `updated_at` from the request's clock, not a trigger, so tests
  with a controllable clock see the value they set.
- **B6.** Every endpoint carries `#[utoipa::path]` with its error responses, and appears in
  `openapi/stepclimb.json`; `just openapi-diff` fails when it does not.

### Organizations and `OrgScope`

- **B7.** An organization is one row in `organizations` (`id`, `slug`, `name`, `settings`,
  `branding`), the table the skeleton migration `20261112000001_organizations.sql` created. It
  is the tenant: every other table carries `org_id` or reaches it through a parent named in its
  spec. That migration is applied and is not edited; this spec adds new ones.
- **B8.** `stepclimb_core::OrgScope` is a `Copy` value holding an organization id and the origin
  it came from (`Session`, `ApiKey`, `AppToken` or `Instance`). Its fields are private. Every
  repository function in `stepclimb-core` takes an `OrgScope` and every query it runs filters by
  `org_id = scope.org_id()`. A query that cannot take one (the credential lookup that produces
  the scope, the instance-wide plan and built-in role rows) says why in a comment beside it, as
  `.claude/rules/architecture.md` requires.
- **B9.** An `OrgScope` is built in two ways only:
  1. **From a credential.** The credential resolvers in `08-sessions-and-csrf.md` (browser
     session, app access token, API key) read the organization from the credential's user or
     service account row and return the scope with origin `Session`, `AppToken` or `ApiKey`.
     The constructor is `pub(crate)` in `stepclimb-core`, so only those resolvers, which are
     core repository functions, can call it.
  2. **By the instance itself.** `OrgScope::instance(org_id)` is public and is listed in
     `clippy.toml` under `disallowed-methods`. The only call sites allowed (each with
     `#[expect(clippy::disallowed_methods, reason = "...")]`) are: startup tasks (B26, and the
     plan and role sync in `09` and `10`), the `stepclimb admin` CLI (B27), job workers once
     they exist (M1), and the request-organization resolver for unauthenticated routes (B11).
     `just lint` fails on any other call.
  An id from the client (a path parameter, a body field, a cursor, a header) never builds or
  changes an `OrgScope`.
- **B10.** An authenticated request's organization is the credential's organization. A user
  belongs to exactly one organization (`users.org_id`, `03-users-and-identities.md`), so there is
  nothing to switch inside one session.
- **B11.** Unauthenticated routes that need an organization (the sign-in start and callback in
  `04` to `06`, the admission flow in `07`) get it from the `RequestOrg` extractor:
  - with exactly one organization on the instance, every request resolves to it;
  - with none (a fresh install before B27 has run), the extractor answers 503 with code
    `org.none` and a `detail` naming `stepclimb admin create`;
  - with two or more, resolution is pending Q2. Until Q2 is decided the extractor answers 404
    `org.not_found` for every request on a multi-organization instance, so no request is ever
    matched to the wrong organization.
- **B12.** The default install has one organization and the web app hides the organization
  switcher (`11-app-shell.md`). M0 adds no API that lists organizations: a principal only ever
  sees its own.
- **B13.** `GET /api/v1/organization` returns the caller's organization (`id`, `slug`, `name`) to
  any authenticated principal. `PATCH /api/v1/organization` changes `name` (trimmed, not empty,
  length limit pending Q6) and needs `perm::OrgManage`. The slug is not changed through the API
  in M0 (pending Q3). A `PATCH` without `name` changes nothing: it answers the organization as it
  is and `updated_at` does not move. `"name": null` is not an omitted name: the schema's `name`
  is not nullable, so it answers 400 `request.malformed`. The settings `PATCH` follows the same
  rules: a patch naming no key writes nothing and leaves `updated_at` alone, and a member sent
  as `null`, under any key, answers 400 `request.malformed` (omit a key to leave it as it is). A
  422 for unknown settings keys lists at most the first 20. `GET /api/v1/me` answers its
  organization with the same `Organization` schema as `GET /api/v1/organization` (coordinator
  decisions, 13 Nov 2026).
- **B14.** `organizations.settings` is read and written only through the typed `OrgSettings`
  struct in `stepclimb-core`. Each key is owned by the spec that uses it (for example the email
  matching setting in `03-users-and-identities.md`, the local sign-in method switches in
  `04-local-accounts.md`, sign-up and sync-only mode in `07-admission.md`), with a default in
  code, so a stored object missing a key reads as that default and no migration backfills
  settings. `GET /api/v1/organization/settings` returns every key with its effective value;
  `PATCH /api/v1/organization/settings` takes a partial object, validates each key it names,
  refuses unknown keys (422 `request.invalid`, `errors[].code = "settings.unknown_key"`) and
  writes the merged object in one statement. Both need `perm::OrgManage`.
- **B15.** `organizations.branding` belongs to `12-tokens-and-theme-generator.md`; this spec
  neither reads nor writes it.

### Accounts

- **B16.** Inside an organization, accounts form a tree. Each account has a `name`, a parent
  (none for the root) and `settings` (a JSON object; M0 defines no keys and the API does not
  expose it). Every organization has exactly one root account, created in the same transaction
  as the organization (B26) and named after it.
- **B17.** `accounts.path` is an `ltree` whose labels are the account ids of the root, every
  ancestor and the account itself, in order, each written as 32 lowercase hex digits (the UUID
  without hyphens, which is a valid label in every PostgreSQL version). Ids never change, so
  renaming touches only `name`, and "A is in B's subtree" is `a.path <@ b.path`.
- **B18.** Creating an account takes `parent_id` and `name`. The parent must be visible to the
  caller (B23) and in the caller's organization; the new path is the parent's path plus the new
  id. The repository computes the path; the client never sends one.
- **B19.** Renaming changes `name` and `updated_at` only.
- **B20.** Moving an account takes a new `parent_id`. The root cannot be moved (409
  `account.root_immutable`). The new parent cannot be the account itself or one of its
  descendants (409 `account.move_into_descendant`). The move rewrites the path of the account
  and every descendant in one `UPDATE ... WHERE org_id = $1 AND path <@ $old` statement and sets
  `updated_at` on each of them, since each one's path and depth change. A move to the account's
  current parent changes nothing: no path is rewritten and no `updated_at` moves (coordinator
  decision, 13 Nov 2026).
- **B21.** Deleting an account is allowed only for a non-root account with no child accounts and
  no role assignment scoped to it (409 `account.root_immutable`, 409 `account.has_children`, 409
  `account.has_assignments`). Assignments are removed first through the role-assignment routes,
  which apply `09-permissions-and-roles.md` B14 and the externally-managed rules; deleting the
  account never removes one behind them. This replaces deleting the account's assignments in the
  same transaction (decided by the owner, 13 Nov 2026). The delete locks the account row
  before looking for assignments, so an assignment created concurrently either refuses the
  delete or finds the account gone. From M1 an account that holds courses also refuses
  deletion; the courses spec adds that check.
- **B22.** Create, move and delete take a transaction-scoped advisory lock keyed on the
  organization id (`pg_advisory_xact_lock`) before reading the tree, so two concurrent moves
  cannot build a cycle and a create cannot attach to an account being deleted. Renames do not
  take it. Coordinator decision (2026-11-13): the routes for create, move and delete take the
  lock first, then repeat the B23 check on the account, its parent and the destination as read
  under the lock, and write in the same transaction, so a move committed after the `Require`
  extractor's check cannot carry any of them out of the caller's reach unseen. A rename reads the
  account row `FOR UPDATE` (which waits for a move in progress over it), repeats its check on
  that path and renames in the same transaction. Coordinator decision (2026-11-13): a create or
  move that would put an account deeper than Q6's maximum depth of 16 (counted as `depth`
  counts it, 0 for the root: 16 levels below the root, 17 in all; `accounts::MAX_DEPTH` from
  issue 3) answers 409 `account.too_deep`.
- **B23.** Account permissions apply to a subtree (`09-permissions-and-roles.md`). An account is
  visible to a principal that holds any permission at a scope containing it: the organization,
  the account itself or one of its ancestors. A principal holding `perm::AccountManage` at
  account A may create accounts under A or any descendant, and rename A or any descendant; it may
  move or delete only strict descendants of A, and only to a new parent inside A's subtree. A
  move whose destination is outside every subtree where the caller holds `AccountManage` answers
  404 `account.not_found` for the destination, as for any id the caller cannot see.
  A move may not widen the caller's own permissions. After the move every grant on the
  destination's path contains the moved account, so every permission effective for the caller at
  the destination must already be effective for them over the moved account; otherwise the move
  answers 403 `permission.escalation` and changes nothing. A destination inside the account's own
  subtree is left to B20's 409 (decided by the owner, 13 Nov 2026).
- **B24.** `GET /api/v1/accounts` with `parent_id` lists that account's children, sorted by
  `name` then `id`. Without `parent_id` it lists the top-most accounts the caller can see with
  `perm::AccountView`: the root when the caller holds it at organization scope, otherwise each
  account where it holds `AccountView` and no ancestor of which it can see. "Can see" here means
  holds `AccountView` at: an ancestor made visible only by another permission does not hide its
  descendants from this list (coordinator decision, 13 Nov 2026).
- **B25.** An account response carries `id`, `parent_id`, `name`, `depth` (0 for the root),
  `has_children`, `created_at` and `updated_at`. `parent_id` is shown even when the parent is not
  visible to the caller; reading that parent still answers 404 (the rule protects a resource's
  contents and existence checks, and every caller already knows its organization has a root).

### Creating organizations

- **B26.** `stepclimb_core::organizations::create` is the one function that creates an
  organization. In one transaction it inserts the `organizations` row, its root account and its
  `org_plans` row (`10-entitlements-framework.md`: the unlimited plan, source `selfhost`). It is
  called only with an `Instance` scope path (B9): the CLI (B27) in M0, the operator console in M6.
  The slug is validated by the rule pending Q3; until Q3 is decided the function accepts only
  the format the recommendation names and the database's existing `UNIQUE` constraint refuses a
  duplicate.
- **B27.** On a fresh install the first organization and its first organization admin are
  created by `stepclimb admin create` (the plan's CLI), pending Q1 for its exact arguments and
  for how that admin first signs in. Whatever Q1 decides, the command calls B26, then creates
  the user (`03-users-and-identities.md`) and assigns the built-in Organization admin role at
  organization scope (`09-permissions-and-roles.md`), all in one transaction, and exits non-zero
  with a message naming the problem if any step fails.
  Decided by the owner (13 Nov 2026):
  - While any organization exists, the command refuses with exit 2 and a message naming Q2,
    and writes nothing: a second organization would make `RequestOrg` answer 404 to every
    unauthenticated request (B11) until Q2's resolution by host exists. It counts the
    organizations under a lock on the table that holds until its commit, so two runs at once
    cannot both create one. This replaces Q1's "run again with a new slug, it adds another
    organization" until Q2 is built.
  - The command ships without Q1's one-time setup link. That link is an enrollment link
    (`04-local-accounts.md` B6, B10, Q7), whose table and function `04-local-accounts.md` issue
    I2 delivers, and I2 adds the printed link to this command. Until then, on success the
    command prints one line to stderr saying the admin has no sign-in method yet and that the
    setup link arrives with local accounts.

  Coordinator decisions (2026-11-13), on the owner's delegation:
  - Before creating anything the command applies the pending migrations and writes the built-in
    roles and the `unlimited` plan, as `stepclimb serve`'s startup does, so the Organization
    admin role exists on an instance where `serve` has never run.
  - The arguments are Q1's: `--org-slug`, `--org-name`, `--email` (the admin's email, which
    local sign-in finds the user by) and `--name` (the admin's display name). The user is
    `local`, `active`, with locale `en` and time zone `UTC` (the default of the organization's
    default time zone, `03-users-and-identities.md` Q4).
  - Exit codes follow `check-config`: 0 on success; 2 when an organization exists or a value is
    refused (an invalid or reserved slug, a blank or too long organization name, an email that
    is blank or contains control or invisible characters, a blank name, or a missing argument),
    naming the flag; 1 when the database fails. On success it prints the organization's slug
    and id and the user's email and id to stdout, and no secret.
  - A failure before the commit says nothing was created. A failed commit says the outcome is
    unknown and to check whether the organization exists. A failure while preparing the
    database says no organization was created but the migrations or the role and plan sync may
    have run.

## API

Errors common to every route below: 400 `request.malformed`, 401 `auth.unauthenticated` (or a more
specific `auth.*` code from `08-sessions-and-csrf.md`), 415 `request.unsupported_media_type`,
500 `internal.error`. Routes with a permission add 403 `permission.denied`.

| Method and path | Request | Response | Errors | Permission |
| --- | --- | --- | --- | --- |
| `GET /api/v1/organization` | | 200 `Organization` | | authenticated |
| `PATCH /api/v1/organization` | `{ "name"?: string }` | 200 `Organization` | 422 `request.invalid` | `perm::OrgManage` (organization) |
| `GET /api/v1/organization/settings` | | 200 `OrgSettings` | | `perm::OrgManage` (organization) |
| `PATCH /api/v1/organization/settings` | partial `OrgSettings` | 200 `OrgSettings` | 422 `request.invalid` (`settings.unknown_key`, per-key codes) | `perm::OrgManage` (organization) |
| `GET /api/v1/accounts` | `?parent_id&cursor&limit` | 200 `Page<Account>` | 400 `pagination.invalid_cursor`, 404 `account.not_found` (parent) | `perm::AccountView` (any scope; filtered, B24) |
| `GET /api/v1/accounts/{account_id}` | | 200 `Account` | 404 `account.not_found` | `perm::AccountView` (account) |
| `POST /api/v1/accounts` | `{ "parent_id": uuid, "name": string }` | 201 `Account`, `Location` header | 404 `account.not_found` (parent), 409 `account.too_deep`, 422 `request.invalid` | `perm::AccountManage` (parent account) |
| `PATCH /api/v1/accounts/{account_id}` | `{ "name"?: string }` | 200 `Account` | 404 `account.not_found`, 422 `request.invalid` | `perm::AccountManage` (account) |
| `POST /api/v1/accounts/{account_id}/move` | `{ "parent_id": uuid }` | 200 `Account` | 404 `account.not_found`, 403 `permission.escalation`, 409 `account.root_immutable`, 409 `account.move_into_descendant`, 409 `account.too_deep` | `perm::AccountManage` (strict ancestor of the account, and the destination) |
| `DELETE /api/v1/accounts/{account_id}` | | 204 | 404 `account.not_found`, 409 `account.root_immutable`, 409 `account.has_children`, 409 `account.has_assignments` | `perm::AccountManage` (strict ancestor of the account) |

Schemas: `Organization { id, slug, name }`; `OrgSettings` (one optional-on-write, always-present-
on-read member per key from B14); `Account { id, parent_id, name, depth, has_children,
created_at, updated_at }`; `Page<T> { items: T[], next_cursor: string | null }`; `Problem { type,
title, status, detail, code, errors? }`.

The unauthenticated `RequestOrg` extractor (B11) has no route of its own; the routes that use it
list `org.none` (503) and `org.not_found` (404) in their own specs.

## Data

Migration `migrations/<timestamp>_accounts.sql` (one per issue; the timestamp is taken when the
issue is implemented):

```sql
CREATE EXTENSION IF NOT EXISTS ltree;   -- trusted since PostgreSQL 13: a database owner can create it

CREATE TABLE accounts (
    id          uuid        PRIMARY KEY,
    org_id      uuid        NOT NULL REFERENCES organizations (id),
    parent_id   uuid,
    name        text        NOT NULL CHECK (btrim(name) <> ''),
    path        ltree       NOT NULL,
    settings    jsonb       NOT NULL DEFAULT '{}'::jsonb CHECK (jsonb_typeof(settings) = 'object'),
    created_at  timestamptz NOT NULL DEFAULT now(),
    updated_at  timestamptz NOT NULL DEFAULT now(),
    UNIQUE (org_id, id),
    FOREIGN KEY (org_id, parent_id) REFERENCES accounts (org_id, id),
    CHECK ((parent_id IS NULL) = (nlevel(path) = 1))
);
CREATE UNIQUE INDEX accounts_one_root ON accounts (org_id) WHERE parent_id IS NULL;
CREATE INDEX accounts_parent ON accounts (org_id, parent_id, name, id);
CREATE INDEX accounts_path ON accounts USING gist (path);
```

The composite foreign key keeps a parent in the same organization as its child, and its default
action, `NO ACTION`, refuses deleting an account that still has children, which backs B21. `UNIQUE (org_id, id)` also lets later tables point at an account with
`(org_id, account_id)` so they cannot reference another organization's account. That the path
matches the parent chain is kept by the repository under the B22 lock and checked by T12; SQL
cannot express it as a constraint across rows.

`organizations` is unchanged (`20261112000001_organizations.sql`). Its `slug` is `UNIQUE` and
case-sensitive; Q3's format makes that effectively case-insensitive if it is lowercase-only.

Repository functions in `stepclimb_core::accounts` (each takes `OrgScope`): `get`, `list_children`,
`list_top_visible`, `create`, `rename`, `move_to`, `delete`, `ancestors_path` (for the
permission evaluator in `09`). In `stepclimb_core::organizations`: `get`, `rename`,
`settings`, `update_settings`, `count` (instance-wide, for B11, commented as such) and `create`
(B26).

## Test cases

Database tests use `#[sqlx::test]`; route tests go through the router with the permission suite from
`09-permissions-and-roles.md` (four cases plus cross-organization). "Org A" and "org B" are two
organizations created by B26 in the same test database.

- **T1** (B1, B2). A malformed JSON body, a body of the wrong content type and a body with an
  empty name each answer the documented status with `Content-Type: application/problem+json` and
  the documented `code`; the 422 lists `errors[].field = "/name"`.
- **T2** (B3). Listing 7 children with `limit=3` returns 3, 3, 1 items across three requests, in
  `name, id` order, with `next_cursor` null on the last; a tampered cursor answers 400
  `pagination.invalid_cursor`.
- **T3** (B3, B9). A cursor produced for org A, replayed by a principal of org B, returns only
  org B rows (never org A's).
- **T4** (B4). Ids created in sequence are UUID version 7 and sort in creation order.
- **T5** (B9). A test file under `crates/stepclimb-server/tests/` that calls
  `OrgScope::instance` without the `expect` attribute fails `just lint` (checked once by hand
  when the lint is added, as a mutation; recorded in the PR).
- **T6** (B11). With one organization, `RequestOrg` resolves to it for any `Host`; with none it
  answers 503 `org.none`; with two it answers 404 `org.not_found` (until Q2).
- **T7** (B13). `GET /api/v1/organization`: anonymous 401; any authenticated principal 200 with
  its own organization; a principal of org B sees org B (cross-organization).
- **T8** (B13). `PATCH /api/v1/organization`: four cases (401; 403 for a user with `AccountManage`
  on the root but no `OrgManage`; 404 does not apply because the target is the caller's own
  organization, which the permission suite records as `OrgTarget`; 200 for an organization admin)
  and the name change is visible to a following GET.
- **T9** (B14). Settings: GET returns every key with its default on a new organization; a PATCH
  naming one key leaves the others unchanged; an unknown key answers 422 `settings.unknown_key`;
  four cases as in T8.
- **T10** (B16, B26). `organizations::create` makes exactly one root account with `depth` 0 and
  an `org_plans` row; a second root insert for the same organization fails on
  `accounts_one_root`.
- **T11** (B17, B18). Creating Tower under the root and Ground under Tower gives
  `path = root.tower.ground` as hex ids; renaming Tower leaves both paths unchanged.
- **T12** (B20, B22). Moving Tower (with two levels below it) under Enroute rewrites the path of
  Tower and every descendant; every account's path then equals its parent's path plus its id.
  Two concurrent moves (Tower under Enroute, Enroute under Tower), run in two connections, end
  with one success and one 409 `account.move_into_descendant`, and no cycle.
- **T13** (B20). Moving the root answers 409 `account.root_immutable`; moving Tower under its own
  child answers 409 `account.move_into_descendant`.
- **T14** (B21). Deleting an account with a child answers 409 `account.has_children`; deleting a
  leaf that a role assignment is scoped to answers 409 `account.has_assignments` and changes
  nothing; once that assignment is removed, deleting the leaf removes it and leaves assignments
  on other accounts.
- **T15** (B23). An account admin of Tower: creates under Tower and under Ground (201); renames
  Tower (200); moves Ground within Tower's subtree (200); cannot move or delete Tower (404,
  because the check is at Tower's parent, which it cannot see); cannot move Ground under Enroute
  (404 for the destination); `GET` Enroute answers 404 and `GET` the root answers 404.
- **T16** (B24). Without `parent_id`, an organization admin sees `[root]`; an account admin of
  Tower and of Enroute sees `[Enroute, Tower]`; an account admin of Tower and of Ground (its
  child) sees `[Tower]` only.
- **T17** (B25). An account admin of Tower reads Tower with `parent_id` equal to the root id and
  `has_children` true.
- **T18** (every account route). Four cases: anonymous 401; a user holding only `AccountView` at
  Tower gets 403 on PATCH, move and DELETE of Ground; an account admin of Enroute gets 404 on
  every Tower route; an account admin of Tower gets the 2xx.
- **T19** (every account route, B9). Cross-organization: an organization admin of org A calling
  each account route with an org B account id (in the path, or as `parent_id` in the body) gets
  404 `account.not_found`, and org B's tree is unchanged.
- **T20** (B27). `stepclimb admin create` on an empty database creates one organization, its
  root account, its plan row, one user and one Organization admin assignment; run again with
  the same slug it exits non-zero and changes nothing (pending Q1 for the arguments).

## Open questions

The owner accepted every recommendation below on 13 Nov 2026. Where a behavior or an issue
says "pending Q<n>" or "Q<n> answered", build the recommended option; the owner can still
overrule one, which then updates this spec.

- **Q1. How the first organization and its first admin are created.** The plan lists
  `stepclimb admin create` in the CLI and says no more.
  - A: `stepclimb admin create --org-slug <s> --org-name <n> --email <e> --name <n>` creates the
    organization (if none has that slug), its root account, its plan row and an organization
    admin, and prints a one-time, short-lived setup link that lets that admin register a passkey
    or password (`04-local-accounts.md`). Run again with a new slug on a multi-organization
    instance, it adds another organization.
  - B: a first-run web setup page served while no organization exists. Simple for self-hosters,
    but whoever reaches a fresh instance first becomes its admin.
  - C: environment variables read at startup (names pending the configuration question in
    `03-users-and-identities.md` Q5) create the organization and admin when the database is empty.
  - Recommendation: A. It needs shell access to the host, which is the trust boundary a fresh
    install already has, and it is the command the plan names.
  **Decided:** the recommendation (owner, 13 Nov 2026).
- **Q2. Which organization an unauthenticated request belongs to on a multi-organization
  instance.** This is the same question as `08-sessions-and-csrf.md` Q1 (which also covers where
  an organization's public origin comes from) and is decided once, there. Options as this spec
  sees them: A, by `Host` (each organization gets a hostname; managed mode already uses
  subdomains and custom domains), which needs a hostname column or setting the data model lacks;
  B, by a path prefix such as `/o/{slug}/auth/...`; C, by a `?org=<slug>` parameter on the
  sign-in routes. Recommendation: A, with the hostname kept in `organizations.settings` until M6
  adds custom domains. A credential from another organization than the request's is treated as
  anonymous (`08-sessions-and-csrf.md` B6).
  **Decided:** the recommendation (owner, 13 Nov 2026).
- **Q3. Organization slug format, reserved slugs and whether a slug can change.** The column
  exists (`text NOT NULL UNIQUE`) with no rule. Options: A, `^[a-z0-9](?:[a-z0-9-]{0,30}[a-z0-9])?$`
  (DNS-label-safe, so it can become a subdomain), with a reserved list (`www`, `api`, `admin`,
  `auth`, `oauth`, `docs`, `app`, `static`, `assets`, `status`, `mail`, `stepclimb`); B, any
  non-empty string, lowercased; C, A without a reserved list. Recommendation: A, and slugs fixed
  after creation in M0 (a rename tool can come with M6 custom domains).
  **Decided:** the recommendation (owner, 13 Nov 2026).
- **Q4. The problem `code` naming scheme and the problem `type` URI.** This spec writes
  `area.reason` in lowercase snake case (`account.not_found`, `request.invalid`). Options for
  `type`: A, `about:blank` everywhere (RFC 9457 then expects `title` to be the HTTP status
  phrase); B, a URL per code under the docs site (`https://<docs>/problems/<code>`), which needs
  the docs domain; C, a relative URI `/problems/<code>` served by the binary. Recommendation:
  `area.reason` codes, and A until the docs site exists in M4, then B.
  **Decided:** the recommendation (owner, 13 Nov 2026).
- **Q5.** (Folded into `03-users-and-identities.md` Q5: the `STEPCLIMB_*` names beyond
  `STEPCLIMB_BIND`, `STEPCLIMB_DATABASE_URL(_FILE)` and `STEPCLIMB_LOG`, and the
  `stepclimb.toml` layout. This spec needs none.)
- **Q6. Input limits.** The plan sets none. Needed: the maximum length of an organization and an
  account name (recommendation: 200 characters), the maximum tree depth (recommendation: 16),
  and the page size (recommendation: default 50, maximum 200, the same for every list).
  **Decided:** the recommendation (owner, 13 Nov 2026).
- **Q7. The UUID v7 library.** Options: A, the `uuid` crate with its `v7` and `serde` features,
  plus sqlx's `uuid` feature; B, a hand-written v7 generator over `rand`. Recommendation: A, run
  through `dependency-researcher` before pinning.
  **Decided:** the recommendation (owner, 13 Nov 2026).
