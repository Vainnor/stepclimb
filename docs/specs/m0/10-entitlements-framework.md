## Summary

An **entitlement** is what an organization's plan allows: a set of feature flags and limits
(users, storage, video storage and transcode minutes, API rate, connectors). This spec builds the
framework from M0 with everything enabled: the feature and limit catalogs in code, the `plans`
and `org_plans` tables, the self-hosted `unlimited` plan every organization runs on, the
`Require<Feature>` extractor that sits next to the permission check, and the limit check. Gating
only bites on managed hosting (M6); self-hosted gets everything, which fits the AGPL license.

## Behavior

### Catalogs

- **B1.** Every feature is a unit struct in `stepclimb_core::feature` implementing the `Feature`
  trait (`const KEY: &'static str`), generated by a macro that also lists it in `feature::ALL`,
  as `09-permissions-and-roles.md` B1 does for permissions. The M0 catalog is Q1's option A:
  `CustomRoles` (`custom_roles`), `OidcProviders` (`oidc_providers`), `Oauth2Providers`
  (`oauth2_providers`), `AdmissionWebhook` (`admission_webhook`), `ApiKeys` (`api_keys`) and
  `CustomBranding` (`custom_branding`); issue 4 puts the checks on their routes. `Feature` is
  sealed as `Permission` is; a build with `stepclimb-core`'s `test-support` cargo feature, which
  only the workspace's tests enable through dev-dependencies, re-exports the seal as
  `feature::TestSeal` so a test crate can define a feature outside `ALL` (B4) (coordinator
  decision, 13 Nov 2026). Plan tiers (which plan includes which feature) are
  deferred to M6 (`docs/plan/technical.md` -> Deferred decisions) and are not decided here.
- **B1a. Key format. Coordinator decision (2026-11-13), for the owner's sign-off before issue 3
  exposes the keys in the API.** Feature and limit keys are one lowercase snake case word
  (`^[a-z][a-z0-9_]*$`: `custom_roles`, `users`), not the `area.action` format that
  `09-permissions-and-roles.md` Q1 chose for permission keys. Permission keys name an action on
  an area; a feature or limit names one thing, and this spec already writes the limit keys
  (`users`, `video_storage`) and Q1's feature names as single words, as the API example below
  shows them. The rule is Q1's for each part (lowercase snake case starting with a letter),
  without the dot. Once issue 3 publishes the keys in `GET /api/v1/organization/entitlements`
  and `/me` they are hard to change, so the owner confirms or overrules this before then.
- **B2.** Every limit is a variant of `stepclimb_core::feature::Limit` with a stable key. The
  plan names the limits: `users`, `storage`, `video_storage`, `transcode_minutes`, `api_rate` and
  `connectors`. M0 adds only `Limit::Users`, because user creation is the only M0 action one
  could exceed; each later limit is added by the spec that builds what it counts (storage and
  video in M1, connectors in M4, API rate with M6's quotas).

### Plans and the self-hosted plan

- **B3.** A plan is a `plans` row with a `key`, a `features` object (feature key to `true` or
  `false`) and a `limits` object (limit key to a non-negative integer, or `null` for no limit).
  Plans are instance-wide rows, not organization data.
- **B4.** The `unlimited` plan (the plan's name for it) has every key in `feature::ALL` set to
  `true` and every limit key set to `null`. The server never reads its `features` or `limits`
  from the row: for an organization on `unlimited` every feature check passes, including a
  feature defined only in a test crate, and every limit is `null`. At startup (before serving; an
  `Instance` scope path, `02-organizations-and-accounts.md` B9) the server upserts the row by key
  so SQL readers see the current catalogs. A feature added in a later release is therefore on for
  every self-hosted organization the moment the binary runs, without a migration.
- **B5.** Every organization has exactly one `org_plans` row. `organizations::create`
  (`02-organizations-and-accounts.md` B26) inserts it in the same transaction: plan `unlimited`,
  source `selfhost`. When the `unlimited` row does not exist yet it inserts it first, with the
  values startup writes, so an organization created before `stepclimb serve` ever ran still gets
  its plan; it never rewrites or locks an existing row, which only startup rewrites (coordinator
  decision, 13 Nov 2026). If startup cannot give an organization its row, the server does not
  start (coordinator decision, 13 Nov 2026). At startup the server also inserts that row for any organization that has
  none, so a database created before this spec's migration is brought into line; it never
  changes an existing row.
- **B6.** M0 has no way to change an organization's plan: no API, no CLI, no Stripe. `ends_at`
  and `stripe_sub` are created as the data model lists them, and M0 code neither writes nor reads
  them. M6 adds plan changes, grants with an end date, the non-profit plan, Stripe and what
  happens when a plan ends.
- **B7.** For any plan other than `unlimited` (none exists in M0 outside tests), a feature key
  missing from `features` reads as `false` and a limit key missing from `limits` reads as `0`, so
  a plan row written before a feature or limit existed fails closed. A stored feature value other
  than `true` reads as `false`, and a stored limit other than `null` or a non-negative integer
  reads as `0` (coordinator decision, 13 Nov 2026). Keys in the row that the
  catalog no longer has are ignored and logged once per startup at `warn`.

### Evaluating entitlements

- **B8.** The request's entitlements are loaded once per request, on first use, with one query
  (`org_plans` joined to `plans` for the principal's organization) and kept in the request's
  extensions so several checks share it. Nothing is cached across requests, so a plan change in
  M6 applies on the next request.
- **B9.** `Require<F>` with `F: Feature` is the same `Require` extractor as
  `09-permissions-and-roles.md` B17 (both catalogs implement its requirement trait), so handlers
  read `Require<feature::X>` next to `Require<perm::Y>`. Order: no principal answers 401 first;
  then a disabled feature answers the status and code pending Q2 (this spec writes 403
  `entitlement.feature_unavailable`); then the permission check runs. A disabled feature is
  reported before the target is resolved, so the answer never depends on whether an id exists.
  Unauthenticated routes that need a feature check it with `Entitlements::require::<F>()` on the
  organization from `RequestOrg` (`02-organizations-and-accounts.md` B11).
- **B10.** `Entitlements::check_room(limit, adding)` answers whether `adding` more units fit.
  When the plan's value is `null` it returns `Ok` without counting, so the unlimited plan never
  runs a count query. Otherwise it counts through the repository function the limit names (for
  `Limit::Users`, `users::count_for_limit` in `03-users-and-identities.md`; which users count is
  M6's to decide with the tiers) and refuses with the status and code pending Q2 (this spec
  writes 403 `entitlement.limit_reached`, with the limit key and the plan's value in the problem's
  `limit` and `max` members). User creation by an admin (`03`), just-in-time creation at sign-in
  (`07-admission.md`) and, in M4, the sync API call it before inserting.
- **B11.** Downgrades never delete data; over-limit features become read-only. That is M6's
  behavior; M0 refuses only new units over a limit and never removes or hides existing ones.
- **B12.** `GET /api/v1/organization/entitlements` returns the organization's plan key and
  source, every catalog feature with its state, and every catalog limit with its value. It needs
  `perm::OrgManage`. `GET /api/v1/me` lists the enabled feature keys for any signed-in user
  (`03-users-and-identities.md` B22) so the web app can hide what the plan does not include; the
  server still checks every request.

## API

Common errors as in `02-organizations-and-accounts.md` -> API.

| Method and path | Request | Response | Errors | Permission |
| --- | --- | --- | --- | --- |
| `GET /api/v1/organization/entitlements` | | 200 `Entitlements` | | `perm::OrgManage` (organization) |

```json
{
  "plan": { "key": "unlimited", "source": "selfhost" },
  "features": { "<feature key>": true },
  "limits": { "users": null }
}
```

Every route that takes `Require<feature::X>` lists the Q2 error (403
`entitlement.feature_unavailable` as written) in its own `#[utoipa::path]`; every route that
calls `check_room` lists `entitlement.limit_reached`.

## Data

Migration `migrations/<timestamp>_plans.sql`:

```sql
CREATE TABLE plans (
    id          uuid        PRIMARY KEY,
    key         text        NOT NULL UNIQUE,
    features    jsonb       NOT NULL DEFAULT '{}'::jsonb CHECK (jsonb_typeof(features) = 'object'),
    limits      jsonb       NOT NULL DEFAULT '{}'::jsonb CHECK (jsonb_typeof(limits) = 'object'),
    created_at  timestamptz NOT NULL DEFAULT now(),
    updated_at  timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE org_plans (
    org_id      uuid        PRIMARY KEY REFERENCES organizations (id),
    plan_id     uuid        NOT NULL REFERENCES plans (id),
    source      text        NOT NULL CHECK (source IN ('stripe', 'grant', 'nonprofit', 'selfhost')),
    ends_at     timestamptz,
    stripe_sub  text,
    created_at  timestamptz NOT NULL DEFAULT now(),
    updated_at  timestamptz NOT NULL DEFAULT now()
);
```

`plans` has no `org_id`: like built-in roles (`09-permissions-and-roles.md` -> Data) it is an
instance-wide definition, and queries on it are commented as such. `org_plans` carries `org_id`
as its key, which gives B5's one row per organization. The `source` values are the data model's.
The `plans.id` of `unlimited` is generated once, by whichever writes the row first (the startup
upsert or `organizations::create`, B5), and stays fixed after.

Repository functions: `stepclimb_core::plans::sync_unlimited` and, for `organizations::create`,
the crate-private `plans::insert_unlimited_if_missing` (both instance-wide, commented),
`stepclimb_core::org_plans::{get_with_plan, ensure_selfhost}` (taking `OrgScope`; the startup
pass calls `ensure_selfhost` per organization with an `Instance` scope).

## Permissions

No catalog entries. `GET /api/v1/organization/entitlements` checks `perm::OrgManage`
(`09-permissions-and-roles.md` B2). The features this spec defines are Q1's (B1).

## Test cases

`#[sqlx::test]` for database tests; routes through the `09` permission suite. Tests that need a
feature off or a limit reached insert a test plan row and point the organization's `org_plans` row
at it by SQL, since M0 has no API for it.

- **T1** (B1, B2). Unit: every key in `feature::ALL` and every `Limit` key is unique and is one
  lowercase snake case word (B1a).
- **T2** (B4). After startup, the `unlimited` row lists every `feature::ALL` key as `true` and
  `users` as `null`; setting one feature to `false` in the row by SQL does not disable it for an
  organization on `unlimited`; a restart rewrites the row.
- **T3** (B5). `organizations::create` leaves one `org_plans` row (`unlimited`, `selfhost`); an
  organization inserted by SQL without one gets it at the next startup; an existing row pointing
  at a test plan is left unchanged.
- **T4** (B7). A test plan with `features = {}` disables every feature; with `limits = {}` refuses
  the first user; an unknown key in either is ignored.
- **T5** (B8). Two `Require<Feature>` extractors on one test route run one entitlements query
  (counted with a query counter on the pool); a plan change by SQL between two requests shows on
  the second.
- **T6** (B9). On a test route taking `Require<feature::X>` and `Require<perm::Y, AccountTarget>`:
  anonymous 401; feature off and an id that does not exist both give the Q2 answer (not 404);
  feature on and permission missing give 403 `permission.denied`.
- **T7** (B10). With the unlimited plan, creating a user runs no count query; with a test plan of
  `users = 2` and two users, `POST /api/v1/users` answers `entitlement.limit_reached` with
  `limit = "users"` and `max = 2`, and inserts nothing.
- **T8** (B12). `GET /api/v1/organization/entitlements`: four cases (401; 403 for a user without
  `organization.manage`; 404 not applicable for `OrgTarget`; 200 for an Organization admin, with
  every catalog feature `true` and `users: null`); cross-organization: an admin of org B sees org
  B's plan.
- **T9** (B12). `GET /api/v1/me` lists every catalog feature for a user on `unlimited` and none
  that a test plan disables.

## Out of scope

- Plan tiers and prices, plan changes, granted and non-profit plans, `ends_at` handling, Stripe
  Checkout, the Customer Portal, Stripe Tax and webhooks, the operator console, quotas and usage
  reporting: M6 (`docs/plan/technical.md` -> Plans and billing, Milestones).
- Read-only mode for over-limit features after a downgrade: M6.
- Limits other than `users`: the specs that build what they count (M1, M4, M6).
- API rate limiting as a plan limit: M6. Rate limits on sign-in and token endpoints are a
  security control, not an entitlement (`08-sessions-and-csrf.md`).
- A switch between self-hosted and managed mode: M6.
- UI for the plan (PlanBadge, UpgradePrompt, UsageMeter): M6 (`docs/plan/ui.md` -> Component
  inventory).

## Open questions

The owner accepted every recommendation below on 13 Nov 2026. Where a behavior or an issue
says "pending Q<n>" or "Q<n> answered", build the recommended option; the owner can still
overrule one, which then updates this spec.

- **Q1. Which features the M0 catalog holds, and which routes check them.** The plan says the
  framework exists from M0 "so gating never has to be added later", and defers which plan gets
  which feature to M6. What can be gated has to be named now for the routes to carry the check.
  Options: A, a feature for each M0 capability a paid tier could plausibly hold back, checked on
  its routes: `custom_roles` (`09` role-writing routes), `oidc_providers` (`05`),
  `oauth2_providers` (`06`), `admission_webhook` (`07`), `api_keys` (`08` keys and service
  accounts), `custom_branding` (`12`); B, one feature per M0 spec area, checked on every route of
  that area, including ones no plan would gate (accounts, users); C, no features in M0, only the
  machinery, with a feature compiled in for tests alone, and each later milestone adds the
  features it introduces. Recommendation: A. It keeps the check on the routes from the start, and
  every listed feature is on for self-hosted and for every M6 tier until the owner sets tiers.
  **Decided:** the recommendation (owner, 13 Nov 2026).
- **Q2. The status and code for a disabled feature and for a reached limit.** Options: A, 403
  with `entitlement.feature_unavailable` and `entitlement.limit_reached`; B, 402 Payment
  Required, which says "upgrade" but is reserved for future use in RFC 9110; C, 404 for a
  disabled feature (as if the route did not exist) and 409 for a limit. Recommendation: A. The
  feature's existence is not secret (it is in `/me` and the docs), and a distinct `code` lets the
  web app show an upgrade prompt in M6.
  **Decided:** the recommendation (owner, 13 Nov 2026).
